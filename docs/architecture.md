# Task Scheduler — Architecture

**Status:** Locked 2026-05-12. Supersedes the 2026-05-04 standalone-only design.

## Mission

A backend service that absorbs every long-running or load-heavy workload that the admin-backend / user-backend generated by the ReactAIClientConfiguration platform cannot serve inline within an HTTP request — and runs all cron-scheduled work — without ever adding latency to a request-serving path.

In-scope workloads (Phase 1): bulk import / update / delete / export of entity rows, scheduled `ActionDefinition`s, recurring system jobs (token cleanup, audit-log retention, stale-upload sweep, job-record cleanup).

Planned (Phase 2, schema designed now): webhook fan-out, email blast, off-request report generation, external-system sync.

## Topology

Two physical components, deployed independently.

### 1. Control-plane (this repo)

- **Path:** `c:\dev\task-schedular\`
- **Role:** scheduler brain. Holds queue state, recurring schedules, artifacts, platform-connection secrets. Dispatches work. Does not execute data-plane runners against project DBs.
- **Database:** own Postgres database `task_scheduler`. Tables: `ScheduledJob`, `RecurringSchedule`, `JobArtifact`, `PlatformConnection`, `Worker`.
- **Stack:** Node 24, TypeScript 5.6, Express 4, Prisma 7.x (aligned with `c:\dev\ReactAIClientConfiguration\app\backend\package.json` — currently `^7.3.0`), Winston, croner, vitest. ESM only.
- **Process model:** one container, two processes (HTTP API + internal worker loop) under a minimal supervisor in `index.ts`. No s6-overlay; the earlier "single image with nginx + UI" decision is dropped because the control-plane has no UI.
- **API surface:** HTTP, backend-only. Endpoints under `/api/jobs`, `/api/schedules`, `/api/artifacts`, `/api/dispatch`, `/api/platforms`, `/healthz`, `/readyz`, `/metrics`.
- **Driver:** `PlatformDriver` interface (`NODE` | `DOTNET`). `NodePlatformDriver` implemented; `DotNetPlatformDriver` is a `NotImplementedError` stub for forward-compat.

### 2. Per-project worker (emitted by the platform)

- **Path:** emitted into `app/output/<slug>/build-N/task-scheduler-worker/` by a new generator in `c:\dev\ReactAIClientConfiguration\app\backend\src\generators\backend\scheduler-worker\`.
- **Role:** thin executor. Long-polls the control-plane for assigned jobs. Runs the appropriate runner against the project's local DB. Reports progress and uploads artifacts back to the control-plane.
- **Database:** the project's own Postgres (via the project's Prisma client). The worker holds **zero** scheduler-side tables — all queue state stays at the control-plane.
- **Stack:** Node 24, TypeScript 5.6, Prisma 6.16 (matches `c:\dev\ReactAIClientConfiguration\app\backend\src\generators\backend\project-scaffold.ts:94` for generated apps).
- **Driver:** also speaks `PlatformDriver`. Same interface, target-specific implementation. Forward-compat with a future .NET re-implementation of the platform stack.

### Flow

```
admin-frontend(X)
  └─ POST /api/customers/bulk-import  (returns job id immediately, p95 < 250 ms)
        │
        ▼
   admin-backend(X)
        │  forward caller JWT + X-Project-Id
        ▼
   control-plane  ─────────►  ScheduledJob row (PENDING, projectId=X)
        ▲                                │
        │ progress, artifacts             │
        │                                ▼
   task-scheduler-worker(X)  ◄── long-poll claim (FOR UPDATE SKIP LOCKED, scoped to projectId)
        │
        ▼
   project DB(X)  ── streamed chunked inserts ──►
```

## Locked decisions

1. **Single control-plane, many workers.** One scheduler deployment serves N registered projects. Per-project workers run inside each generated project's docker-compose, emitted by a platform generator.

2. **Database split.** Control-plane DB stores all queue state and platform secrets. Project DBs receive only data-plane writes. No scheduler models bleed into project schemas.

3. **JWT trust per project.** Each registered project is a `PlatformConnection` row holding an encrypted `jwtSecret`. Control-plane verifies forwarded user JWTs against the secret keyed by `X-Project-Id`. AES-256-GCM with `SCHEDULER_SECRET_KEY` env var.

4. **Service-to-service auth between control-plane and worker.** Worker authenticates with an HMAC bearer token issued at registration. No mTLS in Phase 1.

5. **Dispatch transport is worker-initiated long-poll.** `GET /api/dispatch/claim?workerId=…` blocks up to 30 s, returns 200 with an assigned job or 204 for the worker to reconnect. NAT-friendly; control-plane never needs inbound access to a worker.

6. **`PlatformDriver` abstraction in both components.** Each `PlatformConnection` row carries `targetType: 'NODE' | 'DOTNET'`; a factory selects the implementation at runtime. `NodePlatformDriver` is fully implemented; `DotNetPlatformDriver` throws until requirements arrive.

7. **No control-plane UI in Phase 1.** Operator interactions happen via REST, CLI, and Prometheus. Optional UI lives in a separate phase and a separate repo.

8. **Prisma versions are deliberately split.** Control-plane: 7.x — aligns with the platform's pin in `c:\dev\ReactAIClientConfiguration\app\backend\package.json` (currently `^7.3.0`). Per-project worker: 6.16 — aligns with the generated-app pin emitted by `app/backend/src/generators/backend/project-scaffold.ts:94` (`^6.16.3`). Each component is internally consistent; no shared Prisma client.

9. **Postgres is the only durable substrate.** No Redis, BullMQ, RabbitMQ, Mongo. Claim is `SELECT … FOR UPDATE SKIP LOCKED LIMIT 1` followed by `UPDATE … RETURNING *` via `prisma.$queryRaw` — Prisma's high-level API doesn't express the skip-locked semantics.

## Operating contracts

### Job state machine
`PENDING` → `SCHEDULED` (if `scheduledFor > now()`) → `CLAIMED` (worker holds lock) → `RUNNING` → `SUCCEEDED` | `FAILED` | `CANCELLED` | `RETRYING` | `DEAD_LETTER`

### Claim (control-plane)
```sql
UPDATE "ScheduledJob"
SET status='CLAIMED', "lockedBy"=$workerId, "lockedUntil"=now() + interval '5 minutes',
    attempts = attempts + 1, "startedAt"=now()
WHERE id = (
  SELECT id FROM "ScheduledJob"
  WHERE status IN ('PENDING','RETRYING')
    AND "projectId" = $projectId
    AND "scheduledFor" <= now()
  ORDER BY priority DESC, "scheduledFor" ASC, "createdAt" ASC
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;
```

### Worker registration
`POST /api/dispatch/register { projectId, workerId, capabilities[] }` — control-plane creates a `Worker` row, returns an HMAC bearer token. Worker presents this token on every subsequent request.

### Heartbeat & reaping
Worker calls `POST /api/dispatch/heartbeat/:jobId` every 30 s while a job is running, extending `lockedUntil`. A reaper at the control-plane sweeps jobs whose `lockedUntil < now()` and flips them to `RETRYING` (or `DEAD_LETTER` if attempts exhausted).

### Cancellation
`POST /api/jobs/:id/cancel` flips status to `CANCELLED`. Worker checks status at chunk boundaries, stops cooperatively, writes a partial-results artifact.

### Authentication chain
1. User → admin-frontend → admin-backend (JWT issued by the generated backend).
2. admin-backend → control-plane (`Authorization: Bearer <user JWT>`, `X-Project-Id: <slug>`).
3. Control-plane decrypts `PlatformConnection[X-Project-Id].jwtSecret` and verifies the JWT signature.
4. Control-plane → worker dispatch: HMAC service-to-service token in `Authorization`.

### Multi-tenancy isolation
- One `PlatformConnection` row per registered project.
- Every queue table has a `projectId` column with an FK to `PlatformConnection`.
- Workers can only claim jobs whose `projectId` matches their registration.
- One control-plane DB; cross-tenant queries are not possible because every read predicate carries `projectId`.

## Non-goals (Phase 1)

- Control-plane UI (no React frontend, no admin login).
- Redis / BullMQ / RabbitMQ / Mongo.
- Cross-project job orchestration.
- OpenTelemetry distributed tracing (logs + Prometheus metrics are enough).
- S3 artifact storage (local FS only; S3 is Phase 2).
- Push dispatch (webhooks to workers). Long-poll is the only transport.

## Out-of-scope clarifications

- The platform's own `DeploymentJob` worker (`c:\dev\ReactAIClientConfiguration\app\backend\src\worker.ts`) is unrelated and stays untouched.
- Already-generated projects (`app/output/techahir`, etc.) are not retroactively rebuilt. They opt in by setting `taskScheduler.enabled: true` on the config and regenerating.
- Platform-repo writes are now in-scope (generator additions, schema additions). Supersedes the prior "platform repo is read-only" memory.
